## 1단계: staged 변경사항 확인

아래 명령을 실행합니다:

```bash
git diff --staged
```

출력이 비어있으면 즉시 중단하고 사용자에게 안내합니다:

> "staged 변경사항이 없습니다. `git add <파일>`로 staging한 후 다시 시도해주세요."

`git diff` (unstaged)는 절대 사용하지 않습니다. 커밋되지 않을 내용을 기준으로 메시지를 만들면 혼란을 초래합니다.

## 2단계: 변경사항 분석

diff를 읽고 다음을 파악합니다:

- 어떤 파일들이 변경되었는가
- 각 파일에서 어떤 내용이 추가/수정/삭제되었는가
- 변경의 성격 (기능 추가, 버그 수정, 리팩토링 등)

## 3단계: 커밋 분리 판단

아래 기준 중 하나라도 해당하면 단일 커밋 대신 **커밋 분리를 제안**합니다:

- 서로 다른 type이 섞여 있음 (예: feat + fix, chore + feat)
- 논리적으로 독립적인 모듈/기능이 동시에 변경됨 (예: 인증 로직 + UI 컴포넌트)
- 분리하면 각 커밋이 더 명확하고 되돌리기(revert)가 쉬워지는 경우

커밋 분리가 필요하면:
1. 왜 분리가 필요한지 설명합니다
2. 어떻게 나눌지 (`git add -p` 또는 파일 단위) 안내합니다
3. 각 커밋에 대한 메시지를 모두 제안합니다
4. 클립보드 복사 없이 종료합니다 (어떤 메시지를 쓸지 사용자가 선택해야 하므로)

## 4단계: 커밋 메시지 작성

### 형식

```
<type>: <subject>

<body>
```

`<body>`는 **자동 판단**합니다:
- 변경 파일이 3개 미만이고 변경 내용이 단순하면 → 본문 없이 한 줄
- 변경 파일이 3개 이상이거나 변경 내용이 복잡하면 → bullet 형식으로 본문 추가

### type 선택 기준

| type | 사용 시점 |
|------|----------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 (코드 변경 없음) |
| `style` | 포맷팅, 세미콜론 누락 등 (기능 변경 없음) |
| `refactor` | 리팩토링 (기능 추가도 버그 수정도 아님) |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 빌드, 의존성, 설정 파일 등 |
| `perf` | 성능 개선 |

### 작성 규칙

- subject: 50자 이내, 명령형, 마침표 없음, 한국어
- body의 각 줄: 72자 이내
- 좋은 예: `feat: 사용자 프로필 이미지 업로드 기능 추가`
- 나쁜 예: `fix: 버그 수정` (모호), `feat: 로그인 기능 추가 및 버그 수정` (두 가지 혼재)

## 5단계: 클립보드 복사

커밋 메시지를 확정한 후 클립보드에 복사합니다:

```bash
printf '%s' "<커밋 메시지 전체>" | pbcopy
```

`echo` 대신 `printf '%s'`를 사용합니다. 줄바꿈이 보존되고 특수문자가 안전하게 처리됩니다.

복사 후 사용자에게 안내합니다:

> "클립보드에 복사되었습니다. Cursor에서 Cmd+V로 붙여넣기 하세요."
